# 2. Архитектура проекта iris-api

Date: 2025-12-03

## Status

Accepted

## Context

Нужен учебный/демо-проект для отработки MLOps-подхода:
- обучение модели классификации ирисов;
- развёртывание REST API для инференса;
- трекинг экспериментов и артефактов;
- базовый мониторинг качества данных и модели.

Варианты:
- монолитный скрипт с моделью без API и трекинга;
- Jupyter-ноутбуки плюс отдельный микросервис для предсказаний;
- проект со строгой структурой пакетов и отдельными компонентами для
  данных, модели, API и мониторинга.

## Decision

Строим проект как минимальный, но «правильный» MLOps-сервис со следующей структурой:

- `src/data` — загрузка и разбиение данных;
- `src/models` — обучение модели и сохранение артефактов;
- `src/api` — FastAPI-приложение для инференса;
- `src/monitoring` — отчёты Deepchecks и Evidently;
- `docker-compose.yml` — стенд из `app + mlflow + minio`;
- `deploy/Dockerfile.api` + `deploy/deploy_to_yc.ps1` — образ и скрипт для деплоя serverless-контейнера в Yandex Cloud.

### Обоснование

1. **Чёткое разделение ответственности.**  
   Проще переиспользовать компоненты и заменять реализацию (например, поменять модель, не ломая API).

2. **Лёгкий онбординг.**  
   Структура близка к реальным MLOps-проектам, студентам проще переносить опыт.

3. **Упрощение экспериментов.**  
   Можно отдельно запускать обучение, мониторинг и API, но использовать общие артефакты.

4. **Готовность к CI/CD.**  
   Структура хорошо поддаётся контейнеризации и автоматизации в GitLab CI.

## Consequences

- Любое изменение архитектуры нужно отражать в отдельном ADR.
- Для простых учебных задач проект кажется «тяжеловесным», но это плата за реализм.
- Появляется возможность масштабировать пример до более сложных пайплайнов.
